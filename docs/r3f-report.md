## Як влаштована сцена
- Камера з малим FOV (20°) налаштована так, що на площині карток 1 світова одиниця = 1 CSS-піксель. Позиції, кути (−18, −6, 6, 18°), пропорції, смуга з назвою, скриншот зверху (cover) і рамка читаються з CSS-змінних і computed-стилів `.showcase`, тож 3D збігається з CSS-віялом. Порядок накладання як у CSS.
- Картка: тіло з тонкою фаскою (ExtrudeGeometry, товщина 10 px, ліс-зелені боки), лицьова сторона — CanvasTexture (малюється з тих самих локальних WebP і локальних шрифтів), мандаринова обвідка позаду вибраної картки.
- Освітлення стримане: ambient + одне directional, без тіней, без tone mapping. Біле на картках рендериться ≈ 249–252 з 255, фон hero не змінюється (216, 235, 181).
- Рух: вибрана картка піднімається на 26 px і розвертається (≈ 11°, ліве ребро вперед, щоб назви сусідів не закривалися), сфокусована/наведена піднімається на 20 px (як у CSS); вся група нахиляється за курсором (≤ 3°) і плавно повертається. Нічого не крутиться постійно; немає частинок, bloom, фізики, зовнішніх моделей/CDN.
- Продуктивність: `frameloop="demand"` (кадри лише під час руху), delta-time damping у `useFrame`, анімація через refs без `setState` щокадру, DPR ≤ 1.5, дев'ять draw calls і ≈ 2.8 тис. трикутників, 4 текстури 520×1000, `frameloop="never"` поза viewport (IntersectionObserver), dispose геометрій/матеріалів/текстур/слухачів при знятті сцени.

## Одна модель вибору й доступність
- `selected` живе у `Fan.tsx`; CSS-віяло й сцена використовують той самий стан; клік по картці в canvas викликає ту саму `setSelected`.
- Підпис (назва, тип, технологія, посилання) — той самий DOM-елемент для обох режимів.
- Чотири DOM-кнопки лишаються єдиним способом керування з клавіатури (←/→, Home/End, Enter) у WebGL-режимі. Вони не зникають і не дублюються: стають візуально прозорими, лишаючись на тих самих місцях; фокус-контур видно, сфокусована картка піднімається й у 3D. Canvas у `aria-hidden`, не фокусується; усі назви й посилання доступні без нього.
- Виносна лінія лишилась DOM-елементом: вимірюється по невидимій якорній точці CSS-картки. Розбіжність із 3D картки ≤ ≈ 4 px при нахилі (лінія не перетинає текст).

## Fallback (CSS-віяло лишається справжнім)
Перемикання без зміни висоти hero, без дублювання контролів і без стрибка верстки (перевірено порівнянням координат).
| Сценарій | Поведінка | Перевірено |
|---|---|---|
| до завантаження сцени | CSS-віяло; chunk вантажиться після першого малювання в простої | так |
| `prefers-reduced-motion` | 3D-модуль не вантажиться | так |
| `getContext('webgl')` = null | помилка ловиться `SceneBoundary`, стан `failed`, CSS | так |
| немає `WebGLRenderingContext` | модуль не вантажиться | так |
| помилка завантаження chunk | `catch` → `failed`, CSS | так (запит обірвано) |
| втрата контексту | `webglcontextlost` → `failed`, CSS (до перезавантаження) | так (`WEBGL_lose_context`) |
| звуження до ≤1180 px / повернення | сцена знімається / монтується без повторного завантаження chunk | так |
Діагностика: `?scene=off` примусово вмикає CSS-віяло; `?scene-debug` додає data-атрибути (кадри, draw calls, GPU).

## Правка після огляду: бічне обрізання WebGL-віяла (03.10.2026)

### Причина
Canvas-шар (`.sceneLayer`) мав ту саму ширину, що й колонка `.showcase` (660 px, `left: 0; right: 0`). Картки в CSS-віялі виступають за колонку: на 1440 і 1920 px перша картка виходить ліворуч на ≈ 59 px, остання праворуч на ≈ 58 px (на 1181–1366 px — праворуч до ≈ 44–57 px). У CSS цього ніщо не обрізало (hero має `overflow: hidden` лише по краю сторінки), а WebGL-малюнок обрізався межами canvas. Перевірка координат (камера, світові x, `size`) показала, що розкладка коректна: на ширину canvas x-позиції не залежать, 3D-картки стоять там, де й CSS-картки. Помилка була тільки в розмірі області рендеру.

### Що змінено (найменша надійна зміна)
1. **Ширший canvas**: шар виступає за колонку на `--bleed: 96px` ліворуч, а праворуч на `min(--bleed, --pad)`, тобто не далі за правий відступ hero (там hero однаково обрізає, і сторінка не отримує горизонтального скролу). Висота шару й кадрування по вертикалі не змінені, нижнє обрізання краєм hero лишилося.
2. **Центр сцени**: поля canvas несиметричні, тому сцена зсунута на виміряне `centerX` (центр колонки − центр canvas), яке перераховується через ResizeObserver для колонки та шару. Нахил за курсором і далі обертається навколо центру колонки.
3. **Події**: щоб ширший шар не перехоплював кліки поза картками (текст, CTA), у шару `pointer-events: none`, а R3F слухає події з `.fan` (DOM-кнопки віяла, що збігаються з картками). Вказівник для raycast рахується від меж canvas (власний `compute`: вбудований `eventPrefix` не віднімає зміщення canvas). Кліки поза картками й `.fan` проходять крізь шар. Чутливість нахилу за курсором та сама (нормалізація за шириною `.fan`).
4. **Клік мишею по DOM-кнопці** у WebGL-режимі не забирає фокус (`mousedown.preventDefault`), інакше «фокусний» підйом з'являвся б на сусідній картці. Клавіатура не змінена. Клік, оброблений 3D-сценою, DOM-кнопка не дублює.

### Перевірка (`tools/app_edges.py`, ширини 1181, 1280, 1366, 1440, 1920)
Метод: у кожному стані знімається viewport із canvas і без нього (`visibility: hidden`); різниця дає лише намальоване canvas. Далі міряються крайні пікселі відносно меж шару. Стани: вибір першої та останньої картки; курсор у чотирьох кутах `.fan` та в центрі (максимальний нахил); hover і фокус клавіатурою на крайніх картках; повернення курсора мимо canvas.
- Мінімальний зазор від крайнього пікселя до **лівого** краю canvas: 93 px (1181–1366) і 20 px (1440, 1920). Лівих зрізів немає.
- Праворуч canvas закінчується на краю сторінки (як і hero), тому там зазор вимірюється відносно viewport (див. нижче).
- Горизонтального overflow сторінки немає (`scrollWidth == clientWidth`) на всіх п'яти ширинах.
- Текст, CTA та підпис не перехоплюються canvas (`elementFromPoint` у кутах і центрі кожного елемента); шар має `pointer-events: none`.
- Збіг положення з CSS-віялом: зміщення центру силуету по x ≤ 6 px (1181: 6.0/0.0; 1280: 4.5/−0.5; 1366: 4.5/1.0; 1440: 5.0/−1.5; 1920: 5.5/−1.5 для першої/останньої вибраної). Те саме при симетричному canvas, тобто компенсація центру працює; розбіжність 3–6 px — це поворот вибраної 3D-картки.
- Підсумок `app_edges.py`: 131/131 PASS. Регресія: `app_webgl.py` 65/65, `app_interactions.py` (CSS) 60/60, `app_qa.py` — 0 ширин із проблемами (раніше відразу після розширення canvas на 1440 з'являлося зауваження про елемент ширший за viewport; після обмеження правого поля воно зникло).

### Чесні обмеження
- **Правий край на вузьких ширинах.** Правий край останньої картки в CSS-віялі сам впритул до краю сторінки: гранично CSS виходить за viewport на 3 px (1181), 0 px (1280), не виходить на 1366+ (запас 2–5 px). Нахил за курсором і поворот вибраної картки додають до цього кілька пікселів у крайньому стані «остання вибрана + курсор у лівому куті `.fan`». Вимір до обмеження правого поля canvas (коли шар ще виступав за viewport): 1181 px — до 11 px за краєм сторінки, 1280 — до 3 px, 1366 — 0, 1440 — до 1 px, 1920 — 0. Це обрізання краєм hero/сторінки (так само, як у CSS), а не межами canvas. Усунути його можна лише зсувом розкладки hero (дизайн) або зменшенням нахилу; без вашого рішення цього не робив.
- Піксельні перевірки не замінюють візуального огляду: **я не можу відкрити зображення**, тому скриншоти (`app-previews/edge-fix-*`) мною не переглядались. Файли `*-bounds.webp` містять пунктирний контур меж canvas лише в знімку.
- Chromium із програмним WebGL (SwiftShader). Safari, Firefox, реальні GPU не перевірялись. Площа canvas зросла ≈ на 24 % (819–852 px замість 660), FPS не вимірювався.
- Нижнє обрізання краєм hero, як погоджено, лишилось.
